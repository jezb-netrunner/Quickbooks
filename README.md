## Project

Build **a multi-client accounting platform** for a Philippine CPA practice that does outsourced bookkeeping. One login for the practice; many client companies inside it, each with fully separate books. Think QuickBooks Online Accountant, but built for BIR compliance.

Do **not** write any application code until you have (a) asked me the clarifying questions in the last section, and (b) shown me a schema + folder plan I approve.

## Stack and hard constraints

- Static SPA: **Vite + React + TypeScript + Tailwind**, deployed to **GitHub Pages** (project subpath — configure `base` and a SPA 404 fallback).
- **Supabase free tier** for Postgres, Auth, Storage, Realtime. No custom server, no Node backend, no serverless functions unless you tell me why it's unavoidable.
- Because there is no trusted server tier, **all integrity and access rules must live in Postgres**: RLS policies, constraints, triggers, and SQL functions. Treat the browser as untrusted. The frontend must never be the thing enforcing that debits equal credits or that a user can only see their own clients.
- All schema changes as ordered, idempotent SQL migration files in `/supabase/migrations`. Never hand me SQL to "just run in the dashboard" without also committing it.
- Free-tier discipline: mind row counts, avoid N+1 queries from the client, aggregate in SQL views/RPCs, keep uploaded files small.

## Multi-tenancy model

- `firms` → `clients` → everything else. Every business table carries `client_id NOT NULL` referencing `clients`.
- `memberships` maps `auth.users` to a firm with a role, plus an optional per-client assignment table for staff who only touch some clients.
- RLS on every table, no exceptions. Policies derive access from membership, never from a value the client sends. Write pgTAP or SQL smoke tests proving a user from Firm A cannot read Firm B's rows, and that an unassigned staff member cannot read an unassigned client's rows.
- The UI has one persistent client switcher; the active client is a URL segment (`/c/:clientId/...`), never only in local state.

## Accounting engine (get this right before anything else)

- Real double-entry. `journal_entries` (header: date, period, source, memo, status, created_by) and `journal_lines` (account_id, debit, credit, optional dimensions). Enforce at DB level: every line has exactly one of debit/credit non-zero, amounts non-negative, and per-entry `sum(debit) = sum(credit)`.
- Money as `numeric(18,2)`. Never floats. Standardize rounding for tax computations in one SQL helper.
- **Posted entries are immutable.** No edits, no deletes — corrections are reversing entries. Drafts are editable; posting is a state transition that locks.
- `periods` per client with `open | closed | locked` status. Posting into a closed period is rejected by a trigger, not by the UI.
- Chart of accounts per client, seeded from a PH SME template, with `account_type` driving report classification and a `normal_balance`. Support parent/child accounts and prevent deleting an account that has activity.
- Every source document (sales invoice, official receipt, purchase invoice, expense, cash disbursement, bank line, adjusting entry) posts through the **same** journal API. No document type writes its own bespoke ledger logic.
- Subledgers for AR and AP keyed to customers and vendors, with open-item application of payments and partial payments.

## PH tax and BIR layer

Client-level tax profile drives behavior; the app must handle any PH taxpayer type, not just VAT:

- Entity type: sole proprietor / professional / partnership / corporation / OPC.
- Business tax: VAT 12% vs percentage tax vs VAT-exempt, with registration effective dates.
- Income tax regime: graduated + itemized, graduated + OSD, 8% gross option, RCIT with MCIT for corporations.
- Withholding agent status; EWT rates per expense type; whether the client is subject to withholding on its own sales.

Deliverables in this layer:

- Tax-inclusive vs tax-exclusive entry, with automatic output/input VAT and EWT lines generated by the posting function — not typed in by hand.
- **BIR books of accounts** as reports: General Journal, General Ledger, Cash Receipts Book, Cash Disbursements Book, Subsidiary Sales Journal, Subsidiary Purchases Journal — in the columnar format BIR expects, exportable.
- Data assembly for: 2550Q, 2551Q, 1601EQ/0619E, 1604E, 1701Q/1701A, 1702Q/1702-RT, and SLSP/relief schedules. Produce the figures and a reviewable working paper per form. Do **not** attempt eFPS/eBIRForms submission.
- Per-client compliance calendar of filing deadlines derived from the tax profile, with status per period.
- Certificate tracking: 2307s received (creditable against income tax) and 2307s issued.
- Treat all rates, thresholds, and deadlines as **configuration in a versioned reference table**, effective-dated — never hardcoded in components. I will verify the values; your job is the structure.

## Reports

Trial balance, general ledger drill-down, P&L, balance sheet, cash flow (indirect), AR/AP aging, subsidiary ledgers — all as date-ranged SQL views or RPCs, all drillable to the source entry, all exportable to CSV/XLSX. Add a cross-client practice dashboard: per client, period status, unreconciled items, uncategorized transactions, upcoming deadlines.

## Practice workflow

- Bank/e-wallet CSV import with column mapping saved per client, duplicate detection, and a categorization queue with rules.
- Receipt/document attachments in Supabase Storage, bucket-scoped by client, RLS-protected, linked to entries.
- Immutable audit log of who did what to which record and when.
- Review workflow: staff prepares → reviewer approves → posted.

## Non-negotiables

1. No cross-client data leakage. Ever.
2. Ledger cannot go out of balance through any code path.
3. Closed periods cannot change.
4. No hardcoded tax rates or deadlines.
5. Every migration runs cleanly on a fresh database, in order.
